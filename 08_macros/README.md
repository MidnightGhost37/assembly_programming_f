# 08 — NASM macros: expand, run, compare

**Virtual-class mission:** assemble and run each program, predict its output first, then inspect what NASM generated. Macros are source-code templates expanded at **assembly time**; procedures are machine-code functions called at **run time**. Bring one variation or challenge for discussion.

## Build and run together

Use Linux or WSL with NASM and `ld`. From the repository root:

```bash
mkdir -p build/08_macros
for src in 08_macros/*.asm; do
    name=$(basename "$src" .asm)
    nasm -f elf64 -g -F dwarf "$src" -o "build/08_macros/$name.o"
    ld -m elf_x86_64 "build/08_macros/$name.o" -o "08_macros/$name"
done
for n in m1 m2 m3 m4 m5 m6 m7; do
    echo "===== $n ====="
    "08_macros/$n"
    printf 'exit status: %s\n' "$?"
done
```

The two longer examples use a delay loop of **one billion iterations**. Run them separately and wait for `stop ...`, or press Ctrl+C if time is short:

```bash
./08_macros/macros
./08_macros/procedures
```

The final executables sit beside their `.asm` sources; intermediate object files stay in the ignored `build/` directory. To shorten a class experiment, temporarily change both `1000000000` values to `1000000`, rebuild those two programs, and compare again. A busy loop is a teaching device, not a reliable timer: its duration depends on the machine.

## Inspect values that output hides

`m5` prints a completion message, not its arithmetic results. The three `INCREMENT rax` calls make `RAX=13`; the two `DECREMENT rbx` calls make `RBX=18`. The later write syscall changes `RAX`, so stop **before** it:

```bash
gdb -q 08_macros/m5
```

```text
set disassembly-flavor intel
break _start
run
display/i $pc
si
info registers rax rbx
```

Keep stepping through the three `inc` and two `dec` instructions. Check `RAX` and `RBX` before the subsequent `mov rax, 1`. In pwndbg the same GDB commands work. For `m3`, step through `test` and `jz`, then inspect `eflags`; `test 0,0` sets `ZF`, so execution takes the zero branch.

## Macros versus procedures: the paired experiment

[macros.asm](macros.asm) embeds the `print` and `delay` instruction sequences where each macro is invoked. [procedures.asm](procedures.asm) defines `print:` and `delay:` once and reaches them with `call`, returning with `ret`. Both intend to show:

```text
start ...
stop ...
```

After building, compare their machine-code size and calls:

```bash
size 08_macros/macros 08_macros/procedures
objdump -d -M intel 08_macros/macros | less
objdump -d -M intel 08_macros/procedures | less
```

Find the `call` and `ret` instructions only in the procedure version. Notice how its `delay` receives the count in `RDI`, copies it to `RCX`, and loops. The macro version inserts `mov rcx, %1` at the call site. Both rely on `loop` decrementing `RCX`; unlike `06_loop/01`, there is no syscall **inside** the delay loop to overwrite `RCX`.

**Discuss:** which version is easier to reuse at many call sites? Which version is likely to grow more if the print action is repeated dozens of times? How do argument registers, stack return addresses, and macro parameters differ?

## How to read these programs

Every program here is a 64-bit Linux executable. Several use the same `write` and `exit` system calls:

| Operation | Register | Value in these examples |
|---|---|---|
| Choose `write` | `RAX` | `1` |
| Choose standard output | `RDI` | `1` |
| Address of bytes to write | `RSI` | A `msg` or `newline` label |
| Number of bytes to write | `RDX` | A `len` symbol or `1` |
| Choose `exit` | `RAX` | `60` |
| Exit status | `RDI` | Usually `0` |

`syscall` executes the operation after these registers are set. A label such as `msg1` is an address; `len1 equ $ - msg1` makes an assembly-time constant equal to the number of bytes from `msg1` up to the current location (`$`). The byte `10` is a newline. A macro such as `PRINT` is not a Linux operation; it expands into the register setup and `syscall` instructions.

When a program prints a number, registers alone are not enough. The number must be converted to ASCII digits first. `m2` is the example that performs that conversion.

## `m1.asm`: parameters turn one template into three writes

The macro definition accepts two arguments:

```asm
%macro PRINT 2
    mov rax, 1
    mov rdi, 1
    mov rsi, %1
    mov rdx, %2
    syscall
%endmacro
```

At `PRINT msg1, len1`, NASM substitutes `msg1` for `%1` and `len1` for `%2`. The three invocations generate three sequences of instructions. Each message in the data section already ends with byte `10`, so the macro does not have to print a separate newline.

```text
Welcome to Assembly!
Learning NASM macros.
One macro, multiple messages.
```

**Pause and predict:** what will print if you pass `msg2, len1` by mistake? The macro does not know which length belongs to which address; it copies the two arguments you supply. Inspect the actual string byte counts before trying this, and keep the change in a temporary copy if you do not want to alter the example.

**Debugger task:** break at `_start`, step until the first `syscall`, and inspect `RAX`, `RDI`, `RSI`, and `RDX`. Use `x/s $rsi` to view the bytes addressed by `RSI`. On return from `write`, `RAX` holds the number of bytes written, replacing the syscall number.

## `m2.asm`: macros calculate; a procedure converts and prints

`ADD_NUMBERS 25, 15` expands to `mov rax, 25` and `add rax, 15`, leaving `40` in `RAX`. `SUB_NUMBERS 50, 20` leaves `30`. Neither macro itself prints anything. The program first writes a label (`Addition: ` or `Subtraction: `), then calls `print_number`, then invokes `NEWLINE`.

Follow the first calculation:

```text
write "Addition: "   -> puts a label on screen
ADD_NUMBERS 25, 15  -> RAX = 40
call print_number    -> converts 40 into '4' and '0', then writes them
NEWLINE              -> writes byte 10
```

`print_number` repeatedly divides unsigned `RAX` by 10. Before each `div rbx`, `xor rdx, rdx` clears the upper half of the dividend. The quotient returns in `RAX`; the remainder in `RDX` is one decimal digit. Adding `'0'` turns that digit into its ASCII code. The routine stores digits **backward** from the end of the 32-byte buffer because division discovers the least significant digit first. It then calculates the digit count from the final `RSI` pointer and writes precisely that many bytes.

| Conversion pass for `40` | `RAX` before `div` | Quotient after `div` | Remainder | Byte stored |
|---|---:|---:|---:|---|
| 1 | 40 | 4 | 0 | `'0'` |
| 2 | 4 | 0 | 4 | `'4'` |

Because the pointer moves left before each store, the buffer contains `40` in normal reading order. The loop also prints zero correctly: one division produces remainder zero before `test rax, rax` stops it. It is designed for **unsigned** values; a negative subtraction needs a different conversion path.

**Live task:** change `ADD_NUMBERS 25, 15` to `ADD_NUMBERS 99, 1`. Predict how many conversion passes occur. In GDB, stop at `print_number`, step through `.convert`, and inspect `RAX`, `RDX`, and `RSI` after each division and store.

**Discussion:** `print_number` uses `RBX` without saving it. What should a reusable procedure do if its caller expects `RBX` preserved? How would you add a `push rbx` and matching `pop rbx` without disturbing `ret`?

## `m3.asm`: local labels prevent collisions

`CHECK_ZERO rbx` expands to a `test rbx, rbx`, a conditional branch, one of two write sequences, and a jump past the unused branch. `test` computes a bitwise AND for flags without storing a result. If `RBX=0`, `ZF=1` and `jz` takes the zero branch. If `RBX=25` or `100`, `ZF=0` and the nonzero branch writes its message.

```text
Number is zero.
Number is not zero.
Number is not zero.
```

The macro uses `%%zero` and `%%done`. NASM gives each macro **invocation** its own versions of these labels. Plain `zero:` and `done:` inside a macro called three times would collide. To see the generated labels, run:

```bash
nasm -e 08_macros/m3.asm | less
```

**Predict:** if you add `mov rbx, -1` followed by `CHECK_ZERO rbx`, which branch runs? Does `CHECK_ZERO` test whether a number is positive, or only whether it is exactly zero?

## `m4.asm`: repetition before the program starts

`PRINT_FIVE_TIMES` is a macro with **zero** parameters. Inside it, `%rep 5` makes NASM emit the five-instruction write sequence five times. When the program runs, it proceeds straight through those copies; there is no branch back to the first copy.

```text
Hello!
Hello!
Hello!
Hello!
Hello!
```

Count the write syscalls in the disassembly, then change `%rep 5` to `%rep 3` in a temporary copy and count again. Compare the source size, executable `.text` size, and run-time output. `%rep` is useful when the repeated code is small and expansion is desired; a run-time loop avoids copying the body many times.

**Question:** how would you print a number of times that is only known **after** the program starts? Could `%rep` use such a value?

## `m5.asm`: register changes are not automatically displayed

`INCREMENT rax` expands to `inc rax`; `DECREMENT rbx` expands to `dec rbx`. The arithmetic in `_start` is:

| Step | `RAX` | `RBX` |
|---|---:|---:|
| Initial `mov` instructions | 10 | 20 |
| Three `INCREMENT rax` calls | 13 | 20 |
| Two `DECREMENT rbx` calls | 13 | 18 |

The subsequent write syscall prints only `Register operations completed.` It does not format `13` or `18`. Also, `mov rax, 1` for the syscall overwrites the `13`, so stop before that instruction if you want to see it.

**Live task:** set a breakpoint at the first `mov rax, 1` after the macro calls. Compare `RAX` there with `RAX` immediately after the `write` syscall. Explain both values. To display the arithmetic results, reuse or adapt the decimal conversion idea from `m2`.

## `m6.asm`: a one-argument exit macro

`PRINT msg, len` writes one line. `EXIT_PROGRAM 0` then expands to `mov rax, 60`, `mov rdi, 0`, `syscall`. Unlike a procedure, this macro does not return; the system call ends the process.

Check the status immediately after running the executable:

```bash
./08_macros/m6
echo "$?"
```

Now try `EXIT_PROGRAM 7`, rebuild, and check again. If you run another shell command before `echo "$?"`, you will see that command's status instead. What would happen to code placed after `EXIT_PROGRAM 7` in `_start`? It may be assembled, but successful `exit` never reaches it.

## `m7.asm`: one macro can invoke another

`PRINT_LINE msg1, len1` expands conceptually to `PRINT msg1, len1` followed by `PRINT newline, 1`. NASM expands those nested `PRINT` calls into two write sequences. `_start` calls `PRINT_LINE` twice, giving four writes in total:

| Write | Bytes sent | Effect |
|---|---|---|
| 1 | `First line` | First message, no newline yet |
| 2 | Byte `10` | Ends first line |
| 3 | `Second line` | Second message |
| 4 | Byte `10` | Ends second line |

The message definitions deliberately omit newlines; the wrapper macro adds them. Inspect `nasm -e 08_macros/m7.asm` and the disassembly, then compare this structure with `m1`, where each message already includes its newline.

**Try it:** call `PRINT msg1, len1` directly between the two `PRINT_LINE` calls. Predict whether its text will have a line break. Explain the result in terms of bytes written, not what the terminal seems to infer.

## `macros.asm` and `procedures.asm`: same goal, different mechanism

The macro version inserts `print` instructions twice and a delay loop once. The procedure version contains one `print:` function and calls it twice. A `call` pushes the address to return to; `ret` reads that address from the stack. The macro call has no return-address push because its expanded instructions are already at the call site.

| Point to compare | Macro version | Procedure version |
|---|---|---|
| Passing the message | Macro arguments `%1`, `%2` become operands | Caller sets `RSI` and `RDX` before `call print` |
| Passing the delay | `%1` becomes the count in `RCX` | Caller sets `RDI`; `delay` copies it into `RCX` |
| Returning | Execution falls through expanded instructions | `ret` returns to the address saved by `call` |
| Reusing code | More invocations can duplicate code | More invocations can call the same body |
| Debugger view | Expanded instructions at `_start` | Separate `print` and `delay` symbols |

For these **small** samples, the procedure executable can have more `.text` bytes than the macro executable because it needs `call`, `ret`, and argument setup. Measure the actual versions with `size`; do not assume a procedure is always smaller. As the number of print sites grows, sharing one procedure may save space. Add more print invocations to both temporary copies and measure again.

The delay is a busy loop. `loop` decrements `RCX` and branches while it is nonzero. The procedure's `delay` receives the count in `RDI`; the macro's `delay` receives it as a source argument. Both loops avoid syscalls until they finish, because `syscall` overwrites `RCX`. Neither loop guarantees a precise time delay.

**Paired experiment:** stop at `delay` in the procedure program and inspect the top of the stack (`x/gx $rsp`) before `ret`. Then stop inside the macro-expanded delay and inspect the same location. Which version has a return address from a `call delay`? Explain the difference using the instruction sequences, not just the source names.
